# Defect Classification — Lab 4 Memory and Integer Security Audit

**Original source:** `original/student.c` (exact faculty module, 76 lines, SHA-256 `3de3ffedbc41e951332bcaa36227bd15b97fd5fca1dff5250b2b1b8ac1aff5e4`).

Line numbers below refer to the unchanged saved source. Each row is one underlying defect; where one defect causes several consequences they are described together rather than counted repeatedly.

| ID | Function | Exact source location | Defect category | Technical explanation | Security impact | Severity | Corrective action |
|---|---|---|---|---|---|---|---|
| D-01 | `create_student` | Line 15: `Student *s = malloc(sizeof(Student));` (first dereference at line 18) | Memory allocation failure / null dereference | The return value of `malloc()` is never checked. If allocation fails, `s` is NULL and is dereferenced at lines 18, 19, 20 and 21. cppcheck reports four `nullPointerOutOfMemory` warnings at those lines. | NULL-pointer dereference, process crash, denial of service. | High | Check the result immediately; return NULL on failure before touching any member. |
| D-02 | `create_student` | Line 16: `strlen(name)` | Missing pointer validation / invalid read | `name` is passed to `strlen()` without a NULL check. A NULL argument causes an invalid read inside the C library. | Crash or invalid memory read; can be reachable from untrusted callers. | High | Validate `name` before any length operation and reject NULL. |
| D-03 | `create_student` | Line 18: `malloc(strlen(name))` | Incorrect allocation size / missing string terminator | The allocation reserves exactly `strlen(name)` bytes, omitting the terminating `'\0'`. | Any correctly terminated copy overflows the allocation by one byte; heap metadata corruption is possible. | High | Allocate `length + 1` bytes after a bounded length check. |
| D-04 | `create_student` | Line 19: `strcpy(s->name, name)` | Heap buffer overflow / unbounded string copy | `strcpy()` writes the entire string plus its terminator without any destination-bound information. Combined with D-03, writing `"Alice"` into 5 bytes writes 6 bytes. Valgrind reports an invalid 1-byte write immediately after a 5-byte block. | Heap overflow, memory corruption, possible code execution. | High | Copy exactly the validated length with `memcpy()` into a `length + 1` buffer. |
| D-05 | `create_student` | Lines 16–17: `if (strlen(name) > MAX_NAME) printf(...)` | Ineffective input validation | An oversized name only produces a warning; execution continues into the unsafe copy at line 19. `strlen()` also scans without a bound before the length is known. | Oversized input still reaches the overflow path; warning-only handling gives no failure signal. | Medium | Reject names with length 0 or greater than `MAX_NAME` using a bounded scan and return NULL. |
| D-06 | `create_student` | Line 21: `malloc(count * sizeof(int))` | Memory allocation failure / unchecked array allocation | The `marks` allocation result is not checked, and the object is returned even if it is NULL. Later code dereferences it at lines 29, 36, 49 and 63–67. | NULL dereference and denial of service on allocation failure. | High | Check the allocation; on failure free the name and Student, then return NULL. |
| D-07 | `create_student` | Line 20: `s->count = count;` and line 21: `count * sizeof(int)` | Negative-to-unsigned conversion | `count` is declared `int` at line 13 and stored in `size_t count`. A negative value becomes a very large unsigned value. GCC emits two `-Wsign-conversion` warnings. | Huge count drives an invalid allocation and later out-of-bounds indexing. | High | Accept `size_t count` in the API and reject zero; validate all signed caller input before conversion. |
| D-08 | `create_student`, `resize_marks` | Lines 21 and 41: `count * sizeof(int)` / `new_count * sizeof(int)` | Allocation-size multiplication overflow | The product is computed without checking whether it fits in `size_t`. A large count can wrap to a small byte count. | Undersized heap allocation followed by out-of-bounds writes; memory corruption. | High | Check `count <= SIZE_MAX / sizeof(int)` before multiplying and only then allocate. |
| D-09 | `calculate_total` | Line 28: `i <= s->count`, read at line 29 | Out-of-bounds read / off-by-one | The loop runs while `i <= count`, so it reads `marks[count]`, one element past the array. That slot is also uninitialised in the normal run. Valgrind reports an invalid 4-byte read just beyond a 20-byte block. | Invalid read, uninitialised value use, incorrect totals, possible disclosure of adjacent heap data. | High | Use `size_t i` and the condition `i < s->count`. |
| D-10 | `calculate_total` | Line 29: `total += s->marks[i]` | Signed integer overflow | `total` is a 32-bit `int` and additions have no range check. Summing several `INT_MAX` values is undefined behaviour and can wrap to a negative total. | Incorrect grade totals and undefined behaviour that compilers may exploit. | High | Accumulate in `int64_t` with explicit `INT64_MAX`/`INT64_MIN` guards before each addition; return a status. |
| D-11 | `add_bonus` | Line 36: `s->marks[i] += bonus` | Signed integer overflow / partial update | Each element is incremented without testing whether the result exceeds `INT_MAX` or falls below `INT_MIN`. Earlier elements are already modified when a later element overflows. | Undefined behaviour plus inconsistent array state if failure is detected mid-loop. | High | Prevalidate all results in `int64_t`; if any is out of range, change nothing and return failure. |
| D-12 | `resize_marks` | Line 41: `s->marks = realloc(s->marks, ...)` | Unsafe reallocation / lost pointer | `realloc()`'s result overwrites the only pointer to the original allocation. On failure it returns NULL and the original block is leaked and unreachable. | Memory leak and permanent loss of student marks. | High | Store the result in a temporary pointer; update `s->marks` only after a non-NULL result. |
| D-13 | `resize_marks` | Line 39 (`int new_count`) and lines 41–42 | Invalid array count / negative-to-unsigned conversion | `new_count` is signed, is converted to an unsigned size expression, and is stored into `size_t count` without validation. Zero and negative values are not handled. GCC emits two more `-Wsign-conversion` warnings. | Reallocating with a wrapped size and an invalid count enables huge or zero-sized allocations and inconsistent object state. | High | Accept `size_t new_count`, reject zero, and validate the byte size before reallocating. |
| D-14 | `resize_marks` | Lines 41–42 (grown array) | Uninitialised memory access | When the array grows, `new_count - old_count` new slots are left indeterminate. `display_student()` at line 49 then reads and prints them. Valgrind reports use of uninitialised values created by `realloc()`. | Information disclosure of stale heap contents and nondeterministic output. | Medium | Zero the newly added region before publishing the new count. |
| D-15 | `calculate_total`, `add_bonus`, `resize_marks`, `display_student`, `destroy_student` | Lines 25, 33, 39, 45, 52 (parameters `Student *s`) | Missing argument validation | Every function dereferences its `Student *` without checking it, and `display_student()` also assumes `name` and `marks` are valid. | NULL input crashes the process; invalid object state is not detected. | Medium | Validate object and required member pointers in every entry point and return a failure status or diagnostic. |
| D-16 | `destroy_student` | Line 56: `free(s->name)` (first free at line 54) | Double-free / invalid deallocation | The name pointer is freed twice. cppcheck reports `doubleFree` and Valgrind reports an invalid free of an already-freed 5-byte block. | Heap allocator corruption, crashes, exploitable memory-management state. | High | Free `name` exactly once, then `marks`, then the object; null the caller's pointer. |
| D-17 | `main` | Line 74: `printf("First mark = %d\n", student->marks[0]);` after line 73 | Use-after-free | `destroy_student(student)` frees the object and its members, then `main` dereferences the stale pointer. Valgrind reports an invalid 8-byte read from a freed Student block and an invalid 4-byte read from freed marks. | Stale-memory read, crash, possible disclosure of reused heap data. | High | Read any required value before destruction; change `destroy_student` to take `Student **` and null the caller pointer. |
| D-18 | `main` | Line 62: `create_student("Alice", 5)`, dereferenced at line 63 | Unchecked constructor result | `main` never checks whether `create_student()` succeeded before writing `student->marks[0]`. | On allocation failure the program dereferences NULL and crashes. | High | Check the returned pointer and return `EXIT_FAILURE` with a diagnostic if NULL. |
| D-19 | `calculate_total`, `add_bonus`, `display_student` | Lines 28, 35, 48 (`int i` versus `size_t count`), print at line 49 | Unsafe index type / signed-unsigned comparison | Loop indices are `int` but are compared against `size_t count`, producing three GCC `-Wsign-compare` warnings. An `int` index cannot represent counts above `INT_MAX` and negative values convert to huge unsigned values. | Index range errors and portability/type-safety defects. | Medium | Use `size_t` indices and the `%zu` format specifier. |

## Categories inspected but not confirmed

- **Wrong `free()` pairing (e.g. `free` on stack memory):** all `free()` calls target heap pointers, so this is not reported.
- **`memcpy`/`memmove` overlap:** no such calls appear in the original.
- **Zero-size allocation from `realloc`:** `new_count == 0` is covered by D-13 rather than claimed as a separate portable `realloc(ptr, 0)` outcome.
- **Explicit integer truncation to a narrower type:** the original converts signed to unsigned and performs unchecked arithmetic, but has no explicit narrowing cast; truncation is prevented in the remediation rather than reported as an original defect.
- **Memory leak in the normal execution path:** Valgrind reports "All heap blocks were freed" for the original run because the double free compensates for the lost realloc pointer by accident. The unsafe realloc (D-12) remains a real defect under allocation failure; no normal-path leak is claimed.
